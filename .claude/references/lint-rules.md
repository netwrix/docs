## Dale (model-checked)

- **exclamatory-sentences**: This rule should trigger when the user or agent writes exclamatory sentences. (Message: Don't use exclamatory sentences.)
- **idioms**: This rule should trigger when the user or agent uses an idiom or other culturally specific expression. (Message: Don't use idioms. Write what you mean more directly and literally.)
- **minimizing-difficulty**: This rule should trigger when the documentation minimizes task difficulty—for example, 'With [product], you can easily [task].' (Message: Do not minimize the difficulty of tasks users are performing.)
- **misplaced-modifiers**: This rule should trigger when the documentation has a misplaced or dangling modifier. This includes participial phrases that attach to the wrong subject (e.g., '[participle phrase], [wrong subject] [verb]') and modifying clauses placed too far from the word they describe (e.g., '[noun A] [preposition] [noun B] [modifier that actually describes noun A]'). (Message: Avoid misplaced modifiers. Move the modifier, or descriptive phrase, so that it accurately describes the right thing.)
- **negative-assumptions**: This rule should trigger when the user or agent writes something that assumes a user cannot do something without the product. (Message: Don't make negative assumptions about what users can or cannot do.)
- **passive-voice**: This rule should trigger when the user or agent writes a sentence or clause in passive voice. (Message: Don't use passive voice. Use active voice instead.)
- **positional-references**: This rule should trigger when the documentation uses spatial direction words like 'below', 'above', 'as shown below', or 'the above section' to reference other content. (Message: Avoid positional references like 'below', 'above', or 'as shown below'. Use 'the following' or a named anchor instead.)
- **undefined-acronyms**: This rule should trigger when a product-specific or non-standard acronym is used without being spelled out on first use in body prose, following the pattern: 'File System Access Audit (FSAA)' on first use, then 'FSAA' thereafter. Do NOT flag: well-known IT industry standards that a sysadmin audience would know (DNS, AD, IP, HTTP, TCP, SID, UID, CPU, RAM, URL, SQL, OS, VM, API, SSH, SSL, TLS, LDAP, SAML, MFA, ACL, DACL, SACL, OU, GPO, NTFS, etc.); code literals in backticks; Netwrix product short names when the full product name has already appeared in the article; acronyms that appear only in headings or titles (define-on-first-use applies to body prose only). Do flag product-specific acronyms like AIC, FSAA, SPAA, CEE, AMQP when used in body text without prior definition, even if the article's title or subject implies the reader knows them. (Message: Acronym used without being defined on first use. Spell it out: 'Full Name (ACRONYM)'.)
- **wordiness**: This rule should trigger when the user or agent writes a wordy sentence when a more concise, direct alternative is possible without altering the meaning. (Message: This sentence is wordy. A more concise, direct alternative is possible.)
- **xy-slop**: This rule should trigger when the user or agent writes something in the negative-postive form, for example 'x is not y, x is z'—or similar. (Message: Do not use the 'x is not y, x is z' format.)
